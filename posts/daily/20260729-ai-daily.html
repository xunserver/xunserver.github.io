Agent / Skill / MCP / 开发工具 ​

MCP 2026-07-28：协议核心转向无状态架构 ​

  • 具体变化：
    • 移除原有 initialize / initialized 握手与协议级 Session；
    • 每次请求通过 _meta 携带协议版本、客户端信息与能力；
    • 新增 server/discover，用于客户端按需发现服务端能力；
    • HTTP 请求可由任意 MCP Server 实例处理，不再要求 sticky session 或共享会话存储；
    • 新增 Mcp-Method、Mcp-Name 等标准化 Header，便于网关路由、限流与审计；
    • 工具及资源列表结果支持 ttlMs 和 cacheScope，使客户端可安全缓存能力列表。
  • 适用场景：
    • Kubernetes、Serverless、多实例远程 MCP Server；
    • 需要经过 API Gateway、Load Balancer、WAF 或统一鉴权层的企业 MCP；
    • 大规模 Agent 平台、工具市场及多租户工具接入层。
  • 可能影响：
    • 远程 MCP Server 可以更接近普通无状态 HTTP 服务，显著降低横向扩容复杂度；
    • 网关无需深度解析 JSON-RPC Body，即可基于 Header 实现路由、限流和观测；
    • 依赖 Mcp-Session-Id、旧握手流程或 SSE 恢复机制的实现需要迁移；
    • 应用状态不会消失，但应通过显式 handle，例如 browser_id、task_id 或业务资源 ID，在工具参数中传递。
  • 是否值得立即尝试：值得在测试环境立即尝试，生产环境暂缓全量升级。这是一次包含 breaking changes 的基础协议重构，应先完成 client/server 兼容矩阵、回退策略和观测验证。
  • 核查来源：
    • MCP 2026-07-28 Release Candidate 与最终发布时间说明
    • MCP Go SDK v1.7.0 Release

MCP Extensions：MCP Apps 与 Tasks 成为正式扩展 ​

  • 具体变化：
    • MCP 建立正式 Extensions Framework，扩展可以独立于核心规范演进；
    • MCP Apps 允许 Server 提供可在宿主中沙箱渲染的交互式 HTML UI；
    • Tasks 从实验性核心能力迁移为扩展，并改为由服务端返回 Task Handle，客户端使用 tasks/get、tasks/update 和 tasks/cancel 驱动生命周期；
    • tasks/list 被移除，避免无 Session 环境中的租户与权限边界问题。
  • 适用场景：
    • 长时间运行的代码生成、研究、数据处理及自动化任务；
    • 需要结构化 UI，而不适合只返回文本或 JSON 的 Agent 工具；
    • 需要把异步任务生命周期标准化的 Agent 平台。
  • 可能影响：
    • MCP 不再只是一层“模型调用工具”的 RPC 协议，而开始覆盖 UI、长任务与扩展治理；
    • 已实现旧版实验性 Tasks API 的系统需要调整任务创建与状态查询流程；
    • Agent Skill 可以逐步拆分为核心 Tool、交互 UI 和长任务扩展三层职责。
  • 是否值得立即尝试：值得做 PoC。尤其适合已经存在自定义异步任务协议或前端 Tool UI 的团队，但目前应避免把所有业务能力都提前绑定到尚未普遍支持的新扩展。
  • 核查来源：
    • MCP 2026-07-28 规范说明

授权、可观测性与 Schema 能力增强 ​

  • 具体变化：
    • 授权流程进一步对齐 OAuth 2.0 与 OpenID Connect，要求校验授权响应中的 iss；
    • 规范化 W3C Trace Context 在 _meta 中的传递方式，可贯通 MCP Client、Server 与下游服务；
    • Tool 的 inputSchema 与 outputSchema 升级到完整 JSON Schema 2020-12；
    • Roots、Sampling、Logging 被正式标记为 deprecated，推荐分别迁移到 Tool 参数/资源 URI、模型供应商 API 和 OpenTelemetry。
  • 适用场景：
    • 企业 SSO、多授权服务器、多租户 MCP；
    • 对审计、Trace、错误定位有明确要求的生产 Agent；
    • 复杂 Tool Schema、联合类型、条件 Schema 和结构化输出。
  • 可能影响：
    • 安全实现不能继续把 MCP OAuth 当作简化版 Web OAuth；
    • 可观测性应从自定义日志回调转向标准 OpenTelemetry；
    • Tool Schema 验证器需要限制 $ref、嵌套深度及验证时长，避免复杂 Schema 带来资源消耗或攻击面。
  • 是否值得立即尝试：安全与 Trace 部分值得优先跟进；完整 Schema 能力则应按实际工具复杂度逐步启用。
  • 核查来源：
    • MCP 2026-07-28 规范说明
    • MCP Go SDK v1.7.0 Release

值得关注的趋势 ​

1. MCP 正从开发者协议进入基础设施协议阶段 ​

无状态化并不是语法层面的优化，而是明确把 MCP 对齐到云原生 HTTP 基础设施。未来 MCP Server 更可能作为标准微服务部署，而不是依赖单机进程、长连接和隐式会话状态的插件。

2. Agent 的状态管理将从隐式 Session 转向显式业务 Handle ​

协议不再替应用隐藏状态。浏览器会话、任务实例、数据库事务或工作区状态，需要通过显式标识符传递。这提高了可审计性和可组合性，但也要求开发者重新划清协议状态与业务状态的边界。

3. Agent 工具层开始分化为 Tool、Task 与 App ​

简单同步调用继续使用 Tool；长周期执行进入 Tasks；需要交互的能力进入 MCP Apps。Skill 设计将更接近传统软件架构中的 API、Job 与 UI 分层，而不是把所有能力都塞进单次 Tool Call。

4. 兼容性治理开始取代快速堆功能 ​

正式的弃用周期、扩展轨道和 Conformance Suite 表明，MCP 正在解决生产采用阶段最关键的问题：协议演进如何避免反复破坏已有 Client、Server 与 Agent Host。

结论 ​

本期不以旧闻或低质量传闻填充篇幅。过去24小时真正值得开发者关注的增量集中在 MCP 2026-07-28：它将远程 MCP 从有状态插件协议推向可横向扩展、可路由、可缓存、可追踪的云原生 Agent 基础设施协议。

已经维护 MCP Client、Server 或 Agent 平台的团队，应立即建立新旧协议兼容性测试；尚未进入 MCP 生产部署阶段的团队，可以直接以无状态模型、显式业务 Handle 和 OpenTelemetry 为新架构基线。
